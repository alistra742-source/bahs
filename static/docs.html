A run outlives the tab

The sweep used to be the HTTP response, so closing the tab, backgrounding the browser or losing signal killed it. It does not any more.

started byits own task on the server, not by your request closing the tabends a reader, nothing else coming backindex.html auto-reattaches, or press resume watching ends whenyou stop it, the named list runs out, or the pool dies to its last proxy a dead poolends the run and reports the checks it never made

A server restart or redeploy still ends an in-flight run: the runs live in the process, deliberately. Only the proxy list and the alert settings are written to disk.

Two rates, always both

checks / srequests the run completed — refusals included verdicts / snames actually resolved. This is the real speed. answeredshare of checks that produced a verdict

A run that is 80% refused is fast on the first number and slow on the second. Both are shown, side by side, so neither can be read alone — a single "per second" figure over a throttled run is the oldest lie in this genre.

Results are verdicts only: available and taken. Refusals, transport errors and unreadable answers are counted as run health, because they say something about a proxy or a platform and nothing at all about the name.

A free name is agreed twice

Free is the one verdict you act on, so it is the one worth a second look. When a check returns available, the same name is asked again through the next proxy — on a rotating endpoint that is a different exit — and only a second available marks it confirmed.
